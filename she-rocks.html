The full story

I designed, built, and maintain the website for the University of Utah’s women’s and nonbinary climbing club. Members create verified accounts, sign up for trips and events, and browse photos and merch, while officers manage events, waitlists, attendance, and outdoor-day scheduling through an admin dashboard.

Under the hood it’s a Django REST API with PostgreSQL and a React frontend, secured with role-based permissions, rate limiting, and token-based authentication. I wrote over 200 automated tests, built a CI pipeline, containerized everything with Docker, and designed an AWS production setup with monitoring and backups. I also audited the app for vulnerabilities and fixed the issues I found before launch.

The details behind the highlights

Registration and scheduling. Events can fill by first-come-first-served or a weighted lottery, with capacity limits and automatic waitlist promotion. The last spot is protected by database row-level locking. The officer scheduling tool finds time slots where at least two officers are free and prevents double-booking across overlapping time ranges. It also uses optimistic concurrency checks, so two officers editing at once can’t overwrite each other’s changes.

Roles and accounts. A three-tier role system (member, officer, admin) enforces permission checks on every API endpoint, and admins control promotion and demotion. Authentication uses JWTs with refresh-token rotation and server-side revocation. Email verification uses signed, expiring tokens, password resets are single-use and expire after an hour, strong passwords are enforced, and login, registration, and reset requests are rate-limited.

Security audit. Besides the privilege-escalation hole that let any member make themselves an admin, the audit turned up personal data exposed through public API responses, rate-limit bypass through spoofed proxy headers, and spreadsheet-formula injection in CSV exports. I fixed all of them. Uploaded images are size-limited, resized, rotation-corrected, and stripped of EXIF metadata, including GPS location, so private location data isn’t republished.

Testing and CI. The 200+ tests include unit, API, and security regression tests. GitHub Actions runs them against both a development configuration and the actual production Docker image, checks for missing database migrations, runs Django’s deployment security checks, and blocks merges on dependency vulnerabilities (pip-audit and npm audit). Weekly scheduled scans and Dependabot updates keep dependencies current.

Infrastructure. The app runs on Docker Compose (Django with gunicorn, PostgreSQL, nginx, and Caddy), hardened for production with multi-stage builds, non-root users, read-only filesystems, dropped Linux capabilities, health checks, and automatic database migrations on deploy. The AWS design uses RDS PostgreSQL with point-in-time recovery, S3 and CloudFront for media, SES for email, and an ALB with TLS. I wrote operations runbooks covering monitoring and alerting (Sentry and CloudWatch), backups, a restore drill, the release procedure, and smoke tests.
